Every post on this blog — this one included — is a plain `.md` file sitting in `_posts/`. Nothing renders it directly; Jekyll turns it into the page you're reading through a fixed pipeline, and understanding that pipeline is really understanding what Jekyll buys you over hand-written HTML.  ## 1. Front matter tells Jekyll what to do with the file  The YAML block at the top of a post — `layout: post`, `title:`, `date:`, `categories:` — isn't part of the content. It's metadata Jekyll reads before rendering anything, and it drives everything downstream: which template wraps the post, what its listed date is, which category pages it belongs to. Strip the front matter and Jekyll doesn't know it's looking at a blog post at all.  ## 2. Layouts wrap content, they don't duplicate it  `layout: post` tells Jekyll to take the rendered Markdown and drop it into `_layouts/post.html` (supplied here by the `minima` theme) — the same template every post uses. The header, footer, and page chrome around this paragraph aren't copied into this file; they exist in exactly one place and get reused for every post automatically. Change the layout once, every post updates.  ## 3. Markdown becomes HTML through `kramdown`  The `**bold**`, `` `inline code` ``, and headings in this file get converted to real HTML tags at build time by `kramdown` (configured in `_config.yml`). Write prose, not markup — the generator handles the tags.  ## 4. Posts list themselves  Nothing on the home page is a hand-maintained list of links. `_layouts/home.html` loops over `site.posts` — a collection Jekyll builds automatically just by scanning every file in `_posts/` and sorting by the date in its filename. Add a file, it appears on the home page. Delete one, it's gone from the list too. No index to update by hand.  ## 5. URLs are generated, not chosen file-by-file  The `permalink` pattern in `_config.yml` (`/:year/:month/:day/:title/` on this site) turns a post's date and filename into its URL automatically. Every post gets a consistent, predictable address without anyone typing out a path.  ## 6. The feed and SEO tags come from the same source  `jekyll-feed` builds `feed.xml` and `jekyll-seo-tag` fills in `<title>` and meta tags — both plugins just read the same posts and front matter everything else already uses. One dataset, several outputs, zero duplicate maintenance.  ## 7. You can preview all of this before it's public  `bundle exec jekyll serve` runs this exact pipeline locally with live reload, so a new post can be checked — rendering, layout, links — before it ever reaches `_posts/` on `main` and triggers a real deploy.  None of this requires a database or a running server. It's Markdown in, a fixed set of generation rules, static HTML out — which is exactly why it fits GitHub Pages so well.
