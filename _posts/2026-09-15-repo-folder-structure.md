Once the [prerequisites]({% link _posts/2026-09-15-jekyll-github-actions-prerequisites.md %})
are in place, this is every file in the repo that's actually load-bearing —
what Jekyll or the GitHub Actions workflow reads, and what happens if it's
missing. Nothing here is decorative; each file earns its place.

```
.
├── .github/
│   └── workflows/
│       └── jekyll.yml
├── Gemfile
├── Gemfile.lock
├── _config.yml
├── _layouts/
│   └── home.html
├── _posts/
│   └── YYYY-MM-DD-title.md
├── about.md
├── index.md
└── .gitignore
```

## `Gemfile` and `Gemfile.lock`

`Gemfile` declares *what* to install: `jekyll` itself, the `minima` theme, and
the two plugins (`jekyll-feed`, `jekyll-seo-tag`) grouped under
`:jekyll_plugins` — that group is a Jekyll convention that tells Jekyll to
auto-`require` those gems as plugins at build time.

`Gemfile.lock` is generated by `bundle install` — it pins *exact* resolved
versions (not just the `~> 4.3`-style ranges from the Gemfile) plus the target
platforms. This file is committed on purpose: it's what makes the GitHub
Actions build reproducible instead of "whatever the latest compatible
versions happen to be today." The `PLATFORMS` section is the thing to watch —
see the prerequisites post for what breaks if it's missing the CI runner's
platform.

## `_config.yml`

Jekyll reads this once, at the start of a build — it does *not* reload on
change during `jekyll serve`, so a config edit needs a server restart. This
one file controls:

- Site-wide variables used in layouts (`title`, `description`, `author`) —
  referenced in templates as `site.title`, etc.
- Which `theme` to use (`minima`), which pulls in that gem's own
  `_layouts/`, `_includes/`, and `assets/` as defaults.
- Which `plugins` to activate at build time.
- The `permalink` pattern that decides post URLs (`/:year/:month/:day/:title/`
  here — hence a post dated `2026-09-15` with filename `...-my-post.md`
  publishes at `/2026/09/15/my-post/`).
- `exclude`, which keeps files like `Gemfile` and `README.md` out of the
  built `_site/` output even though they live in the same directory Jekyll
  scans.

## `_posts/`

Every blog post, one file per post, and the filename format is not a
suggestion: `YYYY-MM-DD-title.md`. Jekyll parses the date straight out of the
filename to sort posts and (with the permalink pattern above) build the URL.
Get the date wrong and the post either sorts out of order or — if the date is
in the future relative to the build's clock — gets silently skipped from the
build entirely.

Each file starts with a **front-matter block** (the `---`-fenced YAML at the
top: `layout: post`, `title:`, `date:`, `categories:`) followed by plain
Markdown. The `layout: post` line is what tells Jekyll which template wraps
the content — in this case, `minima`'s own `_layouts/post.html`, since this
repo doesn't override it.

## `_layouts/home.html`

This is the one layout this repo *does* override. Jekyll's resolution order
for a layout name is: check the site's own `_layouts/` first, and only fall
back to the active theme's `_layouts/` if nothing local matches. `minima`
ships its own `home.html` (used by `index.md`, which sets `layout: home`) that
includes a "subscribe via RSS" link Jekyll generates as a link to raw XML — an
overridden copy of that same file sitting in this repo's `_layouts/` folder
takes priority over the theme's version, with that one line removed. Same
idea applies to `_includes/`, `_sass/`, and `assets/` — any of them can be
overridden per-file without forking the whole theme.

## `about.md` and `index.md`

Two "pages" as opposed to posts — no date in the filename, because they're
not part of the chronological post list. `index.md` sets `layout: home`,
which is what actually renders the post list (see `_layouts/home.html`
above). `about.md` sets `layout: page` (the theme's generic page layout) and
a `permalink: /about/`, which is what makes it reachable as `/about/` instead
of some URL derived from the filename.

## `.github/workflows/jekyll.yml`

The part that turns "files in a repo" into "a live website." Two jobs:

- **`build`** checks out the repo, sets up Ruby (`ruby/setup-ruby`, with
  `bundler-cache: true` so it caches installed gems between runs instead of
  reinstalling every time), runs `actions/jekyll-build-pages` (which reads the
  exact same `Gemfile`/`_config.yml` a local `jekyll build` would), and
  uploads the resulting `_site/` folder as a Pages artifact.
- **`deploy`** — declared with `needs: build`, so it only runs after `build`
  finishes successfully — takes that artifact and publishes it with
  `actions/deploy-pages`.

This job split is why the permissions block at the top of the file
(`contents: read`, `pages: write`, `id-token: write`) exists: only the
`deploy` job actually needs write access to Pages, but permissions are
declared at the workflow level here for simplicity.

## `.gitignore`

Keeps generated output out of version control: `_site/` (the build output —
regenerated every run, never hand-edited), `.jekyll-cache/` and
`.jekyll-metadata` (incremental-build bookkeeping), and `vendor/`/`.bundle/`
(where gems land if you ever run `bundle install --path vendor/bundle`
locally instead of installing system-wide). None of these need to exist in
the repo — GitHub Actions regenerates all of them fresh on every run.

## What's conspicuously *not* here

No `_layouts/post.html`, no `_includes/header.html`, no hand-written CSS file
for the theme. Those all exist — inside the `minima` gem, not this repo —
which is exactly the point made in the previous post: the theme supplies the
boilerplate, and this repo only contains the parts that make this specific
site different from a stock `minima` install.
