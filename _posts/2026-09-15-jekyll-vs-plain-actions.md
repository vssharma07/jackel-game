This repo has actually done both. It started as *Jackal Dash* — a hand-written
`index.html`, `style.css`, and `game.js`, deployed by a GitHub Actions workflow
that did nothing more than upload those files as-is and publish them. Then it
became this blog, built by Jekyll and deployed by a workflow that runs a build
step first. Both use GitHub Actions. Only one of them uses Jekyll. Here's why
that distinction matters once you're publishing blog posts instead of a single
page.

## What "plain GitHub Actions" deployment actually does

For the game, the workflow's job was trivial: check out the repo, hand the
files straight to `actions/upload-pages-artifact`, and deploy them with
`actions/deploy-pages`. No build step, because there was nothing to build — one
page, one stylesheet, one script. GitHub Actions here is just a delivery
mechanism: it moves bytes from the repo to Pages. It has no opinion about what
those bytes are.

That's the right amount of tooling for a single static page. It becomes the
wrong amount the moment you have more than one page that needs to look
consistent — which is exactly what a blog is.

## What Jekyll adds to that same pipeline

Jekyll sits *in front of* the deploy step as a build step. Instead of handing
GitHub Actions finished HTML, you hand it Markdown files and a handful of
templates, and Jekyll generates the HTML. Concretely, for this blog:

- **Layouts and includes replace copy-pasted markup.** Every post on this site
  shares the same header, footer, and page chrome — defined once (in the
  `minima` theme's `_layouts/post.html` and `_includes/`), not copied into
  every post file. Add a fourth post and it automatically gets the same
  header/footer as the other three, because there's only one place that markup
  lives.
- **Content is Markdown, not HTML.** Compare writing `<p>They're small
  compared to wolves...</p>` by hand versus just writing the sentence. Every
  post in `_posts/` is plain Markdown with a small front-matter block — no
  `<html>`, `<head>`, or navigation boilerplate in the file at all.
- **The post list, dates, and permalinks are automatic.** `site.posts` on the
  home page (see `_layouts/home.html` in the theme) loops over every file in
  `_posts/`, sorted by the date in the filename, and generates the URL from
  the `permalink` pattern in `_config.yml`. Add a post; it appears on the home
  page and gets a correct dated URL — nobody hand-edits an index of links.
- **RSS/Atom feed and SEO tags for free.** The `jekyll-feed` plugin generates
  `feed.xml` from the same posts, and `jekyll-seo-tag` fills in `<title>`,
  Open Graph, and meta description tags — both configured once in `Gemfile`
  and `_config.yml`, not maintained by hand per page.
- **Front matter separates metadata from content.** `title`, `date`, and
  `categories` live in a small YAML block at the top of the file, so tooling
  (feeds, post lists, category pages) can read them without parsing prose.

None of this is about GitHub Actions doing more work — the workflow is still
just "build, then deploy." It's about *what gets fed into* that pipeline: raw
HTML you maintain by hand, or Markdown that a generator expands into HTML
consistently, every time.

## Plain HTML vs. Jekyll, side by side

| | Plain static HTML (the old game) | Jekyll blog (this site) |
|---|---|---|
| Adding a new page | Write full HTML, copy header/footer by hand | Write Markdown + front matter |
| Shared header/footer | Duplicated in every `.html` file | Defined once in a layout |
| Post listing | Manually edit a links page | Auto-generated from `_posts/` |
| RSS feed | Hand-write XML, or skip it | Generated by `jekyll-feed` |
| SEO meta tags | Hand-write per page, or skip it | Generated by `jekyll-seo-tag` |
| Right fit for | One page, rarely-changing content | Many pages, frequently-added content |

## How to actually get this running (it's less setup than it looks)

You don't need to hand-build a theme. The whole blog in this repo is five
pieces:

1. **`Gemfile`** — pins `jekyll`, a theme (`minima`), and any plugins:
   ```ruby
   source "https://rubygems.org"
   gem "jekyll", "~> 4.3"
   gem "minima", "~> 2.5"
   group :jekyll_plugins do
     gem "jekyll-feed", "~> 0.17"
     gem "jekyll-seo-tag", "~> 2.8"
   end
   ```
2. **`_config.yml`** — site title, description, and which theme/plugins to use.
3. **`index.md`** with `layout: home` in its front matter — the theme's home
   layout does the rest (lists posts, renders the feed link, etc.).
4. **`_posts/YYYY-MM-DD-title.md`** — one file per post, front matter plus
   Markdown content. That's it; no HTML required.
5. **A two-job GitHub Actions workflow** — `build` (checkout → set up Ruby →
   `actions/jekyll-build-pages` → upload the artifact) then `deploy`
   (`actions/deploy-pages`, gated on `needs: build`). See
   [`.github/workflows/jekyll.yml`](https://github.com/vssharma07/jackel-game/blob/main/.github/workflows/jekyll.yml)
   in this repo for the exact file.

Locally, `bundle install` once, then `bundle exec jekyll serve` gives you
live-reloading preview at `localhost:4000` while you write. Writing a new post
is just adding a Markdown file and pushing — the workflow rebuilds and
redeploys the entire site automatically, feed and all.

## The short version

Plain GitHub Actions deployment is a delivery mechanism — it ships whatever
files you give it. Jekyll is what decides those files don't all have to be
written by hand. For a single page, that extra machinery is overhead. For a
blog — many pages, a growing list of posts, a feed, consistent styling across
all of it — it's the difference between editing Markdown and re-editing HTML
boilerplate every time you have something to say.
